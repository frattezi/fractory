# A dependent Ticket stacks on its blocker's branch

When a Ticket declares exactly one blocker, its Run starts as soon as the blocker's latest Run is done and branches off the blocker's branch, with its pull request based on that branch. It does not wait for the blocker to merge. Auto-merge refuses any pull request whose base is not the repository's base branch, which is exactly the condition "every blocker of mine has merged", so a stack can never land out of order. A Ticket with two or more blockers is not stacked at all: a branch has one parent, so it waits until every blocker has merged and then branches off the base branch like any other Ticket. We chose stacking over simply holding each Ticket until its blocker merged because a Spec is normally split into a chain of tracer-bullet Tickets, and holding makes that chain strictly sequential: ten Tickets become ten merges end to end. The cost is that the factory owns merge order and rebases — a follow-up Run on a blocker leaves every branch above it stale — so a moved blocker tip queues a Restack, and a rebase that conflicts fails the Run for the owner to decide rather than being resolved blind.
